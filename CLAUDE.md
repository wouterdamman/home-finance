# CLAUDE.md

See `AGENTS.md` for conventions, architecture decisions, dev setup, and known gotchas — that file is the canonical instructions doc for this repo and applies equally here.

Claude-specific addenda:

- Before considering a feature "done," click through it in the browser against real or realistic multi-item data — single-item test fixtures have repeatedly hidden real bugs (layout wrapping, split-percentage edge cases) that only show up with more than one row/category/pot.
- For any page with a mobile fork (see AGENTS.md), test at multiple viewport widths (375/390/430px) and verify desktop is pixel-unchanged at ≥768px — a fix that only gets eyeballed at one width has repeatedly hidden real bugs (e.g. a table column squeezing a badge unreadable only appeared once the date column wrapped at exactly 390px).
- When a feature writes data and a *different* feature reads it back (export/import, any serialize-then-deserialize pair), test the actual round trip, not each direction in isolation — checking export's totals/headers looked right missed a scan bug that silently dropped every transaction row for a whole session; only feeding the export back into import surfaced it.
- Before trusting "it's broken" during manual browser testing against local dev servers, verify which process is actually answering the port — a stale docker container or a browser's cached response for an earlier bad server state can produce a confusing "bug" that isn't in the code at all. Check with `lsof`/`curl -D-` and a hard cache-bypass (`fetch(..., {cache:'reload'})` or a fresh incognito-style context) before debugging the app itself.
- Don't trust a client-rendered "success" message for a security-relevant flow (reauth, payment, destructive-action confirmation) as proof the backend actually did what it claims — a UI can show a misleading success page while the server-side write silently failed. When testing this class of flow, cross-check the actual server-side effect (a follow-up API call, a DB row, or — on the deployed cluster — `kubectl logs`) rather than the page's own copy. Found this exact gap: prod's Authentik reauth popup said "Identity confirmed" while the session commit had failed server-side (`gob: type not registered for interface: time.Time`), only visible in the pod logs.
- Never run a mutating `kubectl` command (`patch`/`apply`/`delete`/`scale`/`edit`/forcing an ArgoCD sync, etc.) against the deployed cluster — read-only `kubectl` (`get`/`describe`/`logs`) is fine for diagnosis, but every cluster mutation is Wouter's to run himself. Same caution applies to bulk GHCR package deletion: verify a tagged image's actual manifest-list children via `docker buildx imagetools inspect` before deleting anything "unreferenced" — an untagged digest missing from a plain `gh api .../versions` listing is not proof it's safe to delete (this broke a live prod image pull once already).
- `make dev`'s backend target (`cd backend && go run ./cmd/server`) does not source `.env` on its own — running the backend standalone (e.g. to work around a Makefile issue) fails with `DATABASE_URL not set` unless you `set -a && source .env && set +a` first (plain `source .env` without `set -a` doesn't export the vars to the child process).
- Merging or closing a PR (`gh pr merge`/`gh pr close`) always needs a live "yes" in chat at the moment of execution, even if it was already spelled out and approved in a plan file — plan approval authorizes the scope, not the actual merge/close action itself.
- When two form fields mirror each other live (e.g. a percentage input and its derived amount input), actually type real keystrokes into the derived field during manual testing, not just a single paste/set-and-check — a controlled `NumberInput` whose displayed value is recomputed through the other field on every keystroke can silently garble fast typing (cursor gets reset by the reformat) even though the final computed state looks correct in a screenshot taken after the fact. Found this exact bug in the pot-split percentage/amount editor.
- Always `git push` right after `git commit` on any branch a `gh pr merge` (or another session/workflow reading from origin) will act on next — never assume a local commit is on the remote. Skipping this once merged PR #124 without its last fix commit, which shipped a `NetworkPolicy` selector that could never match (`fromEndpoints` against a `hostNetwork: true` DaemonSet) and took prod's login down.
- After touching anything in the release-please / Renovate digest-pinning / image-tag chain in `deploy/helm/home-finance/values.yaml`, don't trust that a version bump means new content shipped — release-please only rewrites the version text next to `# x-release-please-version`, not a `@sha256:...` digest suffix, so a digest-pinned image tag can silently point at stale content under a new version label. Verify with the pod's actual `kubectl get pods -o jsonpath='{.items[0].status.containerStatuses[0].imageID}'` against the release workflow's logged `containerimage.digest` before trusting a "new version is live" claim. (This repo's own release image is no longer digest-pinned for exactly this reason — see `renovate.json`.)
- If a `release-please` GitHub Actions run fails right after "Successfully opened pull request" (empty `##[error]release-please failed:` with no message), the release PR is missing its `autorelease: pending` label — the action never got to add it before crashing. That silently breaks the *next* run's ability to recognize the PR as a pending release when it's merged: no tag, no GitHub Release, no built image, even though the manifest/CHANGELOG on `main` already say the version bumped. Fix by hand-adding the `autorelease: pending` label to the (already merged) PR via `gh pr edit <n> --add-label "autorelease: pending"`, then push any commit to `main` to retrigger — this is metadata repair that lets CI finish its own job, not a manual tag/version bump, so it doesn't violate "CI must do version bumps."
- `chore(deps)` commits (Renovate's default type for non-security bumps) never trigger a `release-please` version bump or image build on their own — only `feat`/`fix`/breaking changes do. Routine dependency bumps land on `main` but sit unshipped in the image until the next real feature/fix release. Renovate's `vulnerabilityAlerts.semanticCommitType` should be set to `"fix"` so actual CVE patches *do* count as releasable and can't get stuck this way (routine bumps are fine to leave as `chore`).
- Renovate bumping an *indirect* Go dependency (this repo's `renovate.json` explicitly enables that, since transitive modules otherwise never get security bumps) can leave `go.sum` with both the old and new version's hash lines still present, failing CI's `go mod tidy check` step — Renovate doesn't run `go mod tidy` after an indirect-dep-only edit unless `postUpdateOptions: ["gomodTidy"]` is set (now is, in `renovate.json`). If you ever see that check fail on a Renovate PR again, `cd backend && go mod tidy` on the branch and push the fix rather than trying to hand-edit `go.sum`.
- Merging several Renovate Go-dependency PRs back to back can conflict even when each was green individually — `go mod tidy` on one branch removes/adds `go.sum` lines that overlap with another still-open branch's diff once the first is merged. If `gh pr merge` reports a merge conflict on a PR that showed green CI minutes earlier, don't force it — `git reset --hard origin/main` in a worktree for that branch, redo the specific `go get <module>@<version>` + `go mod tidy`, force-push, wait for CI, then merge. It's also common for the rebuilt diff to come back empty — that dependency was already pulled to the target version transitively by an earlier merge in the batch — in which case close the now-redundant PR instead of merging a no-op.
- A backend change that passes `make test-integration` locally has only been proven against *your* database, which has the demo dataset in it. CI's is freshly migrated and empty, and `go test ./...` runs packages in parallel against a single database — both differences have produced red CI on work that was green locally (a test reading the household's carryover pot, which only exists in demo data; two tests in different packages sharing year 2091 while one counted rows for the whole year). Before pushing backend tests, run them against an empty database too — see the Testing section of AGENTS.md for the one-liner — and give each test its own year and month-scoped assertions.
- When a subagent reports its work as verified, re-run the decisive check yourself before pushing: the build, the tests, and for anything user-facing the actual click-through. Three times in one session an agent's "all green" was true only in its own worktree or against its own database, and once it could not drive the browser at all (the dev server serves the main checkout, not a worktree) — which it said plainly, but only because it was asked to. Treat the agent's report as a claim to check, not a result to relay.
